# Design

## Context

See `proposal.md` - Why for the motivation. The facts that shape the approach:

- `backend/src/main/resources/application.properties` sets `spring.jpa.hibernate.ddl-auto=update`. Hibernate therefore creates and alters tables from `Task` at every boot. The DDL it currently emits, captured from the test log, is `create table tasks (id bigint generated by default as identity, completed boolean not null, title varchar(255), primary key (id))`. That statement is the schema this change has to reproduce, by hand, in a migration.
- One entity, one table, no joins, no indexes, no seed data. H2 `2.2.224` in-memory, `ddl-auto=update`.
- Spring Boot `3.3.5` parent manages versions, so new dependencies get no explicit `<version>`: Flyway resolves to `10.10.0`, the PostgreSQL driver to `42.7.4`.
- Flyway 10 unbundled most database support into separate artifacts. `flyway-core` still carries the embedded databases including H2 (there is no `flyway-database-h2` artifact on Maven Central), but PostgreSQL support now lives in `org.flywaydb:flyway-database-postgresql`. So PostgreSQL needs one extra module that H2 does not.
- Existing tests are full-context MockMvc tests against the same H2 instance, with `@Transactional` rollback. They will keep working unchanged if the migrated table is equivalent to the generated one.
- No Docker, no Testcontainers, no CI config in the repo.

## Goals / Non-Goals

**Goals:**
- One reviewed SQL file is the authoritative definition of the schema.
- Startup fails loudly on entity/migration drift instead of silently altering tables.
- The identical migration set runs on H2 and PostgreSQL.
- PostgreSQL support is configuration only: no new module, no new code path, no committed credentials.

**Non-Goals:**
- Not a data backfill or a migration of an existing populated database; there is nothing to migrate.
- Not a seed-data or index-tuning exercise; V1 creates the table and nothing else.
- Not production deployment plumbing: no container, no CI pipeline, no secrets store.
- No entity, repository, service, controller, or frontend changes.

## Decisions

**1. Flyway owns the schema; Hibernate is reduced to a verifier.**
`spring.jpa.hibernate.ddl-auto` becomes `validate`. Spring Boot runs Flyway before the entity manager factory is built, so validation always sees the migrated schema. Rationale: `validate` converts the most dangerous failure mode of this change - a hand-written migration that quietly disagrees with the entity - into a startup error naming the mismatch. Alternatives: `none` (same safety, but a schema that has drifted for other reasons goes unnoticed until a query fails); keeping `update` (defeats the change, since Hibernate would still create and alter tables behind the migration's back).

**2. One portable baseline script, not per-vendor scripts.**
`V1__create_tasks_table.sql` uses only DDL both engines accept: `BIGINT GENERATED BY DEFAULT AS IDENTITY` (H2 2.x and PostgreSQL 10+), `BOOLEAN NOT NULL`, `VARCHAR(255)`, `PRIMARY KEY (id)`. Rationale: the "same migration set on every database" requirement is enforced by the file itself rather than by a rule people have to remember. Alternatives: `SERIAL`/`BIGSERIAL` (PostgreSQL only, fails on H2); `AUTO_INCREMENT` (H2/MySQL only, fails on PostgreSQL); separate vendor-specific locations per database (doubles the surface and lets the two schemas drift silently).

**3. Three dependencies, all version-managed by the Boot parent.**
`org.flywaydb:flyway-core`, `org.flywaydb:flyway-database-postgresql`, and runtime `org.postgresql:postgresql`. Rationale: the parent already pins compatible versions, so an explicit `<version>` would be a second place to update. The PostgreSQL Flyway module is required, not optional, because Flyway 10 moved that support out of the core jar. Alternative: pin Flyway explicitly to decouple from Boot's BOM (rejected: Boot manages the Flyway/JPA integration and an override is a future upgrade hazard).

**4. PostgreSQL is reached through a Spring profile, not a second config tree.**
`application-postgres.properties` sets only the datasource, with env-var placeholders and defaults (`${POSTGRES_URL:jdbc:postgresql://localhost:5432/todo}` and similar) and `spring.h2.console.enabled=false`. Rationale: the project is `.properties`-based, so a profile file matches the existing convention, and placeholders keep credentials out of version control. Alternatives: `application.yml` multi-document profiles (migrates config format for no gain); committed credentials (rejected outright); a separate Spring Boot module (rejected: the migrations are supposed to be shared, not forked).

**5. Default profile stays on in-memory H2; no Testcontainers.**
Rationale: the repo has no container tooling, and adding it would slow every build for a path that is configuration-only. The trade-off is explicit and recorded: the PostgreSQL profile is verified by one manual run, not automatically. Alternative: Testcontainers for genuine CI parity (deferred - see Open Questions).

**6. Flyway's own validation is left on.**
`validateOnMigrate` defaults to `true`, and that default is what enforces the immutability requirement: editing an already-applied migration fails startup with a checksum mismatch. The design therefore adds no configuration for it. Alternative: `spring.flyway.validate-on-migrate=false` (rejected - it would silently accept a rewritten migration).

**7. The existing MockMvc suite doubles as the equivalence test.**
Because `ddl-auto` is `validate`, all seven existing tests now run against a Flyway-created table and Hibernate verifies that table against the entity on context startup. If the baseline and the entity ever disagree, the whole suite fails. On top of that, a dedicated schema test asserts the migration history and the resulting table, and a separate drift test boots a context whose mapping includes a table no migration creates and asserts startup fails.

## Risks / Trade-offs

- [Startup now breaks when an entity gains a field before a migration exists] → Intended. The error names the mismatched column; the fix is always a new migration, never a re-enabled `update`.
- [H2 is in-memory, so V1 is re-applied on every boot and all data is lost on restart] → Expected and unchanged from today. Versioned migrations make the *schema* reproducible; they do not make an in-memory database durable.
- [Pointing the PostgreSQL profile at a database that already has Hibernate-created tables fails with a "non-empty schema without schema history table" error] → No such database exists yet. If one appears, either drop it and let V1 create it, or deliberately set `spring.flyway.baseline-on-migrate=true` for that run. It is not enabled by default, and the rule gets written into `AGENTS.md`.
- [The PostgreSQL path is not covered by an automated test] → Mitigated by keeping it configuration-only and by using vendor-portable SQL, then verifying it once by hand and recording the command in `AGENTS.md`. Testcontainers is the follow-up if the gap becomes annoying.
- [`spring.jpa.show-sql=true` in the base config will be noisy once a real database is attached] → Left alone; cosmetic and out of scope.

## Migration Plan

1. Add the three dependencies, the V1 baseline, `ddl-auto=validate`, and the PostgreSQL profile; add the schema and drift tests; run `mvn -q test`.
2. Verify the PostgreSQL path once by hand: start the app with `--spring.profiles.active=postgres` against a scratch database, confirm `flyway_schema_history` lists V1 and that `GET /api/tasks` answers 200, then record the command in `AGENTS.md`.
3. Rollback before any real database holds data: revert the change. The previous build recreates its own schema via `ddl-auto=update`, so there is nothing to restore.
4. Rollback after a real database exists: a new forward migration, never an edit of V1 - the immutability requirement makes rewriting history impossible by design.

## Open Questions

- Should CI gain a real PostgreSQL run (Testcontainers) once the project has a pipeline? Defers cleanly: it adds a test dependency, not a new decision, and changes neither the specs nor the migration layout.
- Should `spring.jpa.show-sql=true` move to a dev-only profile? Cosmetic; can be decided whenever logging gets noisy.
